# Business Rules

| ID | Rule Definition |
| :--- | :--- |
| BR-01 | User passwords must be at least 8 characters long, including uppercase letters, lowercase letters, numbers, and special characters, without utilizing an interface strength bar. |
| BR-02 | The system strictly separates standard user interfaces (Trainee, Coach) from the dedicated management portal reserved for staff members and administrators (Staff, Admin). |
| BR-03 | New passwords established during password changes or resets must differ from the old password currently stored in the database. |
| BR-04 | Trainee accounts are permitted to register free of charge either directly via email OTP verification forms or through the Google quick sign-up feature. |
| BR-05 | Coach accounts must successfully complete registration and partnership fee payment transactions via integrated payment gateways (VietQR, MoMo) in order to activate the account. |
| BR-06 | Email verification OTP codes must consist of 6 digits and automatically expire after a limited timeframe. |
| BR-07 | Only authenticated users holding the Trainee or Coach role are permitted to create community posts. |
| BR-08 | Post classification is strictly enforced by user role: Trainees can only create Normal or Find Coach posts; Coaches can create Normal, Find Coach, or Find Trainee posts. |
| BR-09 | Post text content must not exceed five thousand characters. |
| BR-10 | Selecting a location is mandatory for every post. |
| BR-11 | A post can contain at most ten media items in total, calculated as the sum of retained existing media items and newly added media items. |
| BR-12 | Duplicate media files are automatically identified and excluded during file selection. |
| BR-13 | Users with locked accounts are strictly prohibited from editing posts. |
| BR-14 | Only the original author can edit their post. |
| BR-15 | A post cannot be edited or deleted if it has been marked as deleted. |
| BR-16 | Content is required for edited posts and cannot be empty or whitespace only. |
| BR-17 | A confirmation dialog is required before finalizing deletion. |
| BR-18 | Package Title is required and must not exceed 255 characters. Package Description must not exceed 500 characters, Target Audience must not exceed 100 characters, and Package Type must be one of BOTH (default), WORKOUT, or MEAL. |
| BR-19 | Package Price (VND) is required and must be between 1,000 VND and 100,000,000 VND (free 0 VND packages are not supported). |
| BR-20 | Package Duration (Days) is required and must be between 1 and 365 days. Optional Session Count must be between 1 and 365 (automatically cleared to null for MEAL-only packages), and optional Minimum Age must be between 1 and 100. |
| BR-21 | When updating a training package, Package Title is required and must not exceed 255 characters; Description and Target Audience must not exceed 500 and 100 characters, respectively. |
| BR-22 | Updated Package Price (VND) is required and must be between 1,000 VND and 100,000,000 VND. |
| BR-23 | Updated Package Duration (Days) must be between 1 and 365 days; optional Session Count (1–365, cleared to null when Package Type is MEAL) and Minimum Age (1–100) must stay within valid bounds. |
| BR-24 | Updating the Price or Duration will only apply to trainees who purchase the package from this point forward; it does not affect the invoices or progress of trainees who previously purchased the package (transaction history logic). |
| BR-25 | Soft-Delete Integrity: Deleting a training package always performs a soft delete by setting IsActive = false (never hard-deleting the row), hiding it from the Coach's active list and the public marketplace while preserving historical orders, training/meal plans, and reviews. |
| BR-26 | Ownership Validation: A Coach can only delete training packages where the CoachId matches their authenticated user ID. |
| BR-27 | All active JWT/session tokens must be immediately revoked and invalidated upon logout to prevent token reuse. |
| BR-28 | The application must disable caching on sensitive management pages so that using the browser's "Back" button after logging out will not display cached restricted data. |
| BR-29 | If no prior completion log exists for the exercise, reviewing it directly creates a completion log with the Coach's decision, feedback, and review timestamp; previously reviewed exercises can also be re-evaluated using Approve or Reject. |
| BR-30 | After every review, the System sends an unread notification to the Trainee reporting the approval or rejection outcome along with the Coach's feedback when provided. |
| BR-31 | Approving an exercise adds it to completed progress counts and recalculates the overall completion percentage (rounded to one decimal place). Once 100% of exercises in the plan are completed, the training plan automatically transitions to completed status. Rejecting an exercise excludes it from completed counts and allows the Trainee to resubmit. |
| BR-32 | Both Staff and Admin have full read and creation access to view and add coach subscription plans within their management privileges. |
| BR-33 | All subscription plan prices must be formatted and displayed in Vietnamese Dong (VND) by default. |
| BR-34 | Only authenticated users with Staff or Admin roles have permission to access, view, search, and filter user account records in the Management Portal. |
| BR-35 | The user account list must display accounts ordered by registration date in descending order (CreatedAt DESC) and support multi-criteria filtering (role: Trainee, Coach, Staff, Admin; status: Active, Locked, All) with pagination (default 10, 20, 50 records per page). |
| BR-36 | Both Staff and Admin have full management privileges (Read, Create, Update, Delete) for Locations in the platform catalog. |
| BR-37 | Location Name is required, must not be empty or consist solely of whitespace, and must not exceed 200 characters in length. |
| BR-38 | Location Name must be unique within the system (case-insensitive validation). No two locations can share the same name. |
| BR-39 | Location Address is optional; if provided, it must not exceed 200 characters in length. |
| BR-40 | Data Integrity Constraint: A Location cannot be deleted if it is currently associated with any existing posts or coach profiles (CoachLocations). The system must enforce referential integrity and reject deletion if active references exist. |
| BR-41 | Deleting a Location requires an explicit confirmation step via a confirmation dialog before executing the permanent removal. |
| BR-42 | Users (Trainee, Coach) are strictly permitted to view and update only their own profile information. Accounts with a "Locked" status are prohibited from editing profile details. |
| BR-43 | Profile Full Name is mandatory, must not be empty or whitespace only, and must not exceed 100 characters. Phone number, if provided, must adhere to a valid phone format. Date of birth must reflect an age of at least 15 years old. |
| BR-44 | Profile avatar uploads must be in valid image formats (JPEG, JPG, PNG, WEBP) and must not exceed 5 MB in file size. |
| BR-45 | Coach profile updates: Years of experience must be a non-negative integer ( 0), biography must not exceed 1,000 characters, and coaches can select up to 5 operating locations and specialty sports from the platform catalog. |
| BR-46 | System Audit Logs are strictly immutable (read-only). No user, including Staff and Admin, is permitted to edit, alter, or delete audit log entries through the interface. |
| BR-47 | Only authenticated Staff and Admin members are permitted to view system audit logs, which record the Actor ID/name, action type, entity type, entity ID, old/new state values, client IP address, and UTC timestamp. |
| BR-48 | Only authenticated Staff and Admin accounts have permissions to review, evaluate, approve, or reject Coach application requests submitted by applicants. |
| BR-49 | Approving a coach application updates ApprovalStatus to "APPROVED", binds the reviewer's ID (ApprovedBy), and activates coach capabilities (publishing training packages, acquiring trainees, receiving client bookings). |
| BR-50 | Rejecting a coach application requires a mandatory rejection reason to be selected/entered, updating ApprovalStatus to "REJECTED" and notifying the applicant of the decision. |
| BR-51 | Only authenticated users with the Administrator (ADMIN) role are permitted to view, create, edit, lock, and unlock Staff accounts. Staff members (STAFF role) are prohibited from managing other staff or admin accounts. |
| BR-52 | Creating a Staff account requires a unique email address, adherence to password complexity requirements (BR-01), mandatory full name, and explicitly sets the internal flag (IsInternal = true) with role STAFF. |
| BR-53 | Locking a Staff account immediately invalidates their active JWT/session tokens (BR-27) and blocks access to the Management Portal. |
| BR-54 | Administrators are strictly prevented from locking their own currently logged-in account to avoid complete administrative lockout. |
| BR-55 | Only authenticated Trainees and Coaches with active (unlocked) accounts are permitted to react to posts. |
| BR-56 | A post cannot receive reactions or be unreacted if it has been marked as deleted in the system. |
| BR-57 | Reaction operates as a binary toggle: a user can maintain at most one active reaction on a post. Clicking the reaction button likes the post, and clicking it again removes the reaction (unlike). |
| BR-58 | Only authenticated Trainees and Coaches with active accounts can report posts. Users are strictly prohibited from reporting their own posts. |
| BR-59 | A post cannot be reported if it has been marked as deleted or is no longer accessible. |
| BR-60 | A user is permitted to submit only one report per post while their previous report for that specific post remains in "Pending" status. |
| BR-61 | A report submission must select exactly one valid predefined reason.If "Other" is selected, an additional explanation is mandatory and must not exceed 500 characters. |
| BR-62 | Submitting a post report does not automatically delete, hide, or alter the post. The system records the report with a "Pending" status and queues it for administrative review by Staff and Admin members in the Management Portal. |
| BR-63 | Meal Plan Assignment & Schedule Bounds: A Meal Plan must belong to the owning Coach and target an Order Detail whose Package Type is MEAL or BOTH (WORKOUT-only packages are rejected). Dates and scheduled weeks must remain within the purchased package validity window (StartDate >= PackagePurchasedAt, EndDate <= PackageEndDate, PlanDays <= DurationDays + 1, WeekNumber <= MaxAllowedWeeks), and the upcoming week (Week 1 on creation, or currentWeek + 1 on update) must contain at least one meal with a non-empty Food Description. Supported Meal Types are Breakfast, Lunch, Dinner, Snack, Pre-Workout, and Post-Workout, with per-meal estimated calories bounded between 0 and 5,000 kcal in the form UI. |
| BR-64 | Training Plan Structure & Exercise Bounds: A Training Plan must belong to the owning Coach and target an Order Detail whose Package Type is WORKOUT or BOTH (MEAL-only packages are rejected). Exercises are organized by Week (1–52, capped at MaxAllowedWeeks = max(1, PlanDays / 7)) and Day (1–7, Monday–Sunday), with mandatory Exercise Name (max 200 chars) and optional Sets, Reps, DurationMinutes, RestSeconds, and Notes (max 500 chars). Total distinct scheduled workout sessions cannot exceed the package's SessionCount (if fixed), the upcoming week cannot be empty unless all sessions are already allocated, and optional tutorial videos may be attached from the Coach's Video Library, a direct video URL, or a Cloudinary video upload (max 100 MB). |
| BR-65 | Plan Publishing & Past-Schedule Immutability: Saving a Training Plan or Meal Plan with status ACTIVE or PUBLISHED sets PublishedAt (if unset) and makes it visible to the trainee, while DRAFT keeps it hidden (PublishedAt = null). When updating an existing plan, StartDate cannot be modified after the schedule has started, and any exercises or meal items scheduled on today's date or earlier are read-only and cannot be added, altered, or deleted; only upcoming future dates can be edited. |
| BR-66 | Direct Chat Eligibility: Any authenticated user may initiate or open a 1-on-1 direct conversation with another existing user (currentUserId != targetUserId); initiating a conversation with oneself is prohibited, and no prior package purchase or mutual friendship is required. |
| BR-67 | Chat Blocking Constraint (Directional): Blocking is directional (UserBlocks: BlockerId -> BlockedId). While blocked by the current user (IsBlockedByMe), the message composer is disabled, outgoing messages are rejected, and unread counts are suppressed (0). If the recipient has blocked the sender (IsBlockedByOther), the sender's messages are saved with MessageType = "BLOCK" (permanently hidden from the blocker) and trigger an automated AUTO reply without SignalR broadcast or notification to the blocker. |
| BR-68 | Unilateral Conversation History Deletion: Deleting a conversation records a per-user UTC deletion timestamp (User1DeletedHistoryAt or User2DeletedHistoryAt) only for the requesting participant, hiding the conversation and prior messages from their view while keeping the channel and history intact for the other participant. If a new message is sent afterward, the conversation reappears showing only messages created after the deletion timestamp. |
| BR-69 | Real-Time Delivery & Notification Fallback: For non-blocked messages, the backend saves the Message, updates the sender's last-read message pointer on Conversation, broadcasts ReceiveMessage via SignalR ChatHub (/hubs/chat) to both participants, and dispatches an unread NewMessage notification (Notification.IsRead = false) to the recipient. Unread chat counts are tracked via User1LastReadMessageId/User2LastReadMessageId, and if SignalR is unavailable, clients fall back to HTTP fetching (GET /api/conversations). |
| BR-70 | Coach Dashboard Metric Isolation: Coach Dashboard KPIs and analytics isolate data strictly to the authenticated Coach's own packages/orders (Orders.CoachId or Package.CoachId) and aggregate revenue/sales only from finalized paid orders (OrderStatus in PAID, COMPLETED, ACTIVE), excluding PENDING, CANCELLED, and REFUNDED orders (while PendingRequestsCount tracks pending/draft items separately). |
| BR-71 | Subscription Price Change Audit & History: Every price update to a CoachSubscriptionPlan is recorded as an immutable audit log entry in AuditLogs (capturing OldPrice, NewPrice, actor ID/name, timestamp, and notes). The Price History view reads these audit records (filtering by FromDate <= ToDate), calculates PriceDifference and PercentageChange, and clamps pagination PageSize between 1 and 100. |
| BR-72 | Platform Revenue Analytics Calculation: FitConnect operates on a 0%-commission model for trainee training packages (CommissionRate = 0; 100% of TraineePackagesGMV belongs to coaches via escrow payouts). Net System Revenue (PlatformDirectRevenue) comes solely from Coach Subscription Plans: PlatformDirectRevenue = max(0, CoachSubscriptionsGMV - ApprovedCoachSubscriptionRefunds), while TotalGMV = TraineePackagesGMV + CoachSubscriptionsGMV and PlatformNetCashHolding = TotalGMV - TotalCoachPayouts - TotalApprovedRefunds. Only finalized orders (PAID, COMPLETED, ACTIVE), APPROVED refunds, and PROCESSED coach payouts are included. |
| BR-73 | Refund Eligibility Conditions & 3-Case Policy: Only the order buyer of a PAID, COMPLETED, or ACTIVE order—who has an active linked refund bank account and whose order has not been paid out to the coach (Payout.Status != PROCESSED)—may request a refund. Requests within 7 days of purchase qualify under Case 1 (100% refund if 0 sessions completed and no plan sent) or Case 2 (deducting completed sessions or 1-session planning effort); requests after 7 days are permitted only when unperformed sessions remain and a coach late-schedule violation is claimed with mandatory image evidence (Case 3 pro-rata refund). |
| BR-74 | Refund Reason & Evidence Validation: A refund request requires a trimmed justification text between 5 and 1,000 characters (Reason). Image evidence (EvidenceUrls) is optional for standard 7-day requests, but at least one evidence image URL is strictly mandatory when filing a complaint for a coach's late schedule violation (Case 3). |
| BR-75 | Single Pending Refund & Access Lifecycle: An order can have at most one PENDING refund request (and no prior APPROVED refund) at any time. Submitting a request transitions the order status to REFUND_PENDING while keeping existing training and meal plan access active; plan access is permanently revoked (403 Forbidden) only when the refund is approved (OrderStatus = REFUNDED). |
| BR-76 | Message Content & Attachment Limits: A message must contain either non-empty trimmed text (maximum 1,000 characters) or at least one valid media attachment. Chat attachments are capped at 5 files per message and uploaded to Cloudinary via /api/upload/post-media, supporting images (JPG, JPEG, PNG, WEBP, GIF) up to 10 MB and videos (MP4, MOV, AVI, MKV, WEBM) up to 100 MB (PDF files are not supported). |
| BR-77 | Message Content & Attachment Limits: Message content length is capped between 1 and 300 characters. Attachments cannot exceed 20MB and must belong to allowed mime types (JPEG, PNG, MP4, PDF). |
